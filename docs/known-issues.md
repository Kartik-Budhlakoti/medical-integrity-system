# Known Issues

Things I know are still broken, deferred, or worth remembering before touching this code again. If something isn't here, treat it as resolved and tested.

## Still open

**File upload validation only checks the extension, not the actual content.** A `.pdf` extension is trusted at face value right now — nothing looks at the real bytes to confirm it. Leaving this for a dedicated security pass later rather than rushing a fix in now.

**Audit log `action` values are just plain strings**, typed out fresh at every call site instead of pulled from one shared list. Since `action` is never set from anything a client sends, this can't be exploited from outside — the real risk is just me spelling something two different ways in two different files, months apart, with nothing to warn me either way. Needs fixing eventually. Not right now.

**No router logs a plain "record not found" (404) — only actual rejections (403/400) get logged.** In `assignment.py` specifically: a nonexistent patient or user ID in `assign()`, and a nonexistent assignment ID in `unassign()`, all fail silently with no audit row. Everything else in that file — bad role, already assigned, deactivated user, not authorized — does log correctly. Same pattern holds across `patient.py`, `treatment_note.py`, and `nursing_note.py`: every 404 lookup is silent, every real 403/400 rejection is recorded. Low priority — these are input mistakes (wrong ID typed in), not suspicious activity — but worth having the actual branches right.

**`entity_type` and `entity_id` on a log row don't always point at the same table.** When something gets rejected before the real record exists yet, I log whatever real ID I actually have on hand — usually a patient's ID — even if `entity_type` still says something else, like "files." Did this on purpose instead of logging a meaningless placeholder. Worth remembering next time something in these logs looks off.

**`patients.height_cm` and `weight_kg` can't be left blank**, which means I can't create a patient record — even during an emergency — without real numbers for both. No bypass exists for that case right now. Fixing it properly means deciding how emergency admission should actually work, not just loosening a constraint.

**Not sure yet whether `POST /files/{file_id}/invalidate` actually deletes the underlying object from B2, or just flags the file record as invalid in the database.** Haven't checked the function body closely enough to know, and the earlier confirmation that deleting from B2 genuinely works may have come from testing that storage function directly, not through this specific endpoint. Need to actually check the code before assuming either way.

**Found a real bug: `is_active` and a bunch of `created_at` columns had no actual default sitting on them in the database**, even though my models all claim they do. Traced it back to an old migration — I added the default to columns that already existed, and the autogenerate tool just doesn't check for that unless I turn a setting on, which I hadn't. Only found out because I ran every migration this project has ever had, from a completely empty database, for the first time, inside Docker. Fixed it there and confirmed it. Still don't know if my regular dev database has the same problem — haven't checked yet. Neon isn't provisioned at all right now, so that check happens whenever I actually set it up, not before.

**Docker is proven across a real set of scenarios now, not just the original bootstrap request.** Through the container, I've confirmed: B2 upload, download, and tamper detection over the real network path; rate limiting actually reaching Valkey, including under real concurrent load; RBAC enforcement on the specialty endpoints, with the rejection itself showing up correctly in the audit log; a missing required secret failing cleanly on first use rather than at startup — though that specific failure leaves no audit trail at all, unlike an explicit rejection; and Postgres going down mid-request recovering on its own once it's back, without the api container needing a restart. Still not tested through the container: an unclean `docker kill` and restart, a near-50MB file upload, and patient creation, assignment, and both note types — none of that has touched the container yet, only bare metal.

**A DB connection killed mid-query** (backend restart while a request is actively running) raises an unhandled OperationalError, not a clean recovery. Confirmed from real postgres logs: restarts during Oct 5–8 show FATAL: terminating connection due to administrator command for a live backend PID, lining up with a raw sqlalchemy.exc.OperationalError: server closed the connection unexpectedly surfacing inside get_current_user. pool_pre_ping=True doesn’t catch this — pre_ping only checks a connection before handing it out of the pool; it can’t protect a query already in flight when the backend dies mid-execution. Different from the recovery noted above, which is about a new request after postgres is back, not a query already running when it goes down. No retry logic exists for this. Fixing it properly means wrapping DB-dependent endpoints in real retry logic, not a quick patch — deferring it rather than rushing it in now.

**Invalidated files are supposed to survive a grace period before actually being deleted from B2** — that part isn’t built, and I’m not planning to build it right now. Checked both pieces: /files/{file_id}/invalidate doesn’t call B2 at all, it only flips the DB row. The bucket’s lifecycle settings are still on “Keep all versions of the file” (the default) — no rule configured. So right now nothing ever deletes an invalidated file’s object from storage — it just sits there indefinitely, with the API’s own access block as the only thing actually enforcing anything. If this ever gets picked up: an explicit hide call belongs in the invalidate route itself (triggered at invalidation, not upload), and the bucket’s lifecycle rule would need to use only daysFromHidingToDeleting — not daysFromUploadingToHiding, which would also purge active files that were never invalidated, based on upload age alone.

## Notes to self

- Some config values only get read once, when the app starts. Editing `.env` while it's already running does nothing until I actually restart it.
- A shell variable I set without exporting it doesn't reliably make it into a server process started afterward. Real values go in `.env`, not typed into the terminal first.
- Inside a `psql` session, `$MY_VARIABLE` isn't a thing — it gets read as a literal, lowercased column name. Learned this the hard way when it happened to match a real column and silently updated six rows instead of one.
- Backblaze keeps deleted files around as hidden versions by default instead of actually erasing them. The app never sees them again, so it doesn't matter functionally, but worth knowing before I'm confused by leftover storage usage later.
- Postgres 18 changed where it wants its data volume mounted — the old path I was used to, `/var/lib/postgresql/data`, gets flat out rejected now. It wants the volume one level up, at `/var/lib/postgresql`, and sorts out its own folder structure underneath that by itself.
- Learned this one the hard way: anything a running container creates on its own, like a migration file generated inside it, only exists in that one container unless I specifically set up a folder to share with my real machine. Almost lost a real migration file this way — caught it just before tearing the container down, moved it out in time. Could easily lose work for good next time if I'm not paying attention.
- Docker's own DNS auto-detection guessed the wrong gateway address on my network — it assumed `192.168.1.1`, but my real gateway (confirmed with `ip route`) was something else entirely. Every outbound connection from inside a container failed because of this, including reaching Backblaze, and nothing about the error pointed at DNS specifically at first — it just looked like a hang. Fixed by setting explicit public DNS servers (`8.8.8.8`, `1.1.1.1`) directly in Compose instead of trusting Docker's own guess. Worth checking `ip route` early next time something inside a container can't reach anything external and the cause isn't obvious.
