# Decisions Log

Real trade-offs I made on this project, and why, written down so I don't have to reconstruct the reasoning from memory later.

## Early on

- Roles live in their own table instead of being a column on `users`. Gives me room for department info and other role-level stuff later without touching the user table itself.
- SuperAdmin exists mainly to stop an Admin from being able to create another Admin: an Admin can only create Doctor and Nurse accounts, and only SuperAdmin can create an Admin. It can also deactivate users and see the doctor list, but not much else. SuperAdmin accounts can't be made through the normal user route at all — only through the one-time bootstrap route, which needs a setup token and refuses once a SuperAdmin exists.
- Notes (treatment, nursing) are append-only. No editing, no deleting — a correction is just a new note, not a change to an old one.
- File integrity gets re-checked on every single access, not just once at upload. That's why the server fetches and re-hashes the actual bytes itself instead of handing back a link — a link would mean I stop being able to promise that guarantee the moment storage moves anywhere else.
- JWTs are stateless — no server-side session tracking. That means changing a password doesn't end sessions that already exist: an old token keeps working until it expires (`ACCESS_TOKEN_EXPIRE_MINUTES` sets how long). Deactivating an account is different — every request looks the user up, so a deactivated user's token stops working right away. Accepting the password-change gap — real session tracking felt like more architecture than this project needs.
- Files are stored under random UUID names on purpose, so nobody can guess or enumerate storage keys. The original filename is kept only in the database.
- Swapped `passlib` and `python-jose` for direct `bcrypt` and `PyJWT`. passlib's last release was in 2020; python-jose went from 2021 to early 2025 without one and has known CVEs — two of them (CVE-2024-33663, CVE-2024-33664) were fixed in 3.4.0, and PyPI's vulnerability data lists others with no fixed release. Wasn't optional, needed doing.
- Invalidated files stay in B2 instead of being deleted right away. Same logic as the append-only notes — I'd rather be able to recover from a wrong invalidation, or show nothing was tampered with after the fact, than destroy the file the instant it's flagged invalid. The API already blocks normal access to it immediately. The delayed deletion itself isn't built yet (see `known-issues.md`), so for now they stay indefinitely.

## Mid-build

- Nursing notes don't store weight. `patients.weight` already exists — storing it twice just means it can quietly drift out of sync with itself.
- Dropped `last_checked_at` entirely instead of finishing it. Same problem as weight — a stored value that has to be kept in sync by hand isn't worth the risk. If I ever need "last checked," I'll compute it from the notes themselves.
- Doctor specialty lives on `users`, not its own table — it's a fact about one person, not shared role data. Locked to a fixed list of values on purpose, since the whole point is filtering by it later, and free text would quietly break that.
- SuperAdmin can't assign or unassign patients. Not a practical use of that role — it's a safety net, not a day-to-day account.
- SuperAdmin can view the doctor list but can't touch someone's specialty. Viewing felt fine; editing clinical-adjacent data didn't.
- Built in a hard block against ever deactivating the last active Admin. Checked live, every time, not assumed.
- An Admin can't deactivate themselves. SuperAdmin can't be deactivated by anyone, period — no exceptions, since it's the one account that has to survive even if everything else gets compromised.
- The upload response includes the real storage key (`file_path`); the file list response doesn't. Seeing exactly where one upload landed is useful while I'm the only one testing it — showing that for every file in a list felt like more exposure than it's worth.
- The doctors list — the one I use to pick someone to assign patients to — leaves out deactivated doctors and is sorted alphabetically by name. A deactivated doctor showing up there would be actively misleading. The patient and file lists don't work that way: doctors and nurses only see patients they're assigned to, patients are sorted newest first, and the file list is newest first and includes invalidated files, shown as inactive.

## Testing

- Kept the tests at full strength instead of making the run faster. Most of the roughly 90-second run is bcrypt: the suite hashes and checks passwords at the same cost the app uses (12). I built a cheaper-cost version that took my run from 88 s to 32 s and passed, then chose not to use it. With a cheaper hash the suite no longer exercises the cost the app really runs with, and I'd rather wait 90 seconds than trust a faster, weaker run.
- Known bugs that the tests find are marked as strict expected-to-fail instead of being fixed on the spot or left red. The run stays green, `pytest -rx` keeps the list of what's broken, and when I fix one its test turns red until I delete the marker — so a fix can't go unnoticed and a bug can't hide. 14 right now (two of the original 16 were fixed before the first deploy); `pytest -rx` lists them.
- Tests are forced onto local file storage, whatever `.env` says, so they can never write to the real Backblaze bucket.
- The test database is dropped and recreated on every run, so `conftest.py` refuses to start unless `DATABASE_URL` points at a database whose name ends in `_test` on `localhost` or `127.0.0.1`. A forgotten `export` stops the run instead of touching anything real.

## Access rules settled while writing tests

- A doctor or nurse who creates a patient isn't automatically assigned to it. Assignment stays an admin-only action, so the creator can't open their own patient until an admin assigns them. Known cost, left as is.
- A doctor or nurse with no assigned patients gets a 403 from the patient list, not an empty list. Left as is rather than changing the route this late.
- "Doesn't exist" (404) and "isn't yours" (403) stay different answers for now, which means a doctor or nurse can tell which patient numbers exist. Known cost, left as is.
- For all three, the tests pin today's behaviour, so changing any of them later means changing that one test on purpose.

## Infrastructure

Facts about outside services (prices, free tiers, limits) are as I found them when I made each decision, and they change. I re-checked the Render, Neon, Azure, AWS and Backblaze ones in October 2026.

- Render for hosting, not Azure. Azure's always-free App Service tier is limited (about an hour of compute a day) and I wasn't confident it could run my Docker setup. The free VM that could is only free for 12 months, which just brings back the "this runs out eventually" problem I was trying to avoid.
- Neon for the database instead of Render's own free Postgres. Render's free database expires 30 days after it's created, with a 14-day grace period before it's deleted (render.com/docs/free, checked 2026-10-21). Neon's free plan has no time limit (Neon's FAQ, checked 2026-10-21) — its compute scales to zero after 5 minutes idle, but the data stays.
- Ruled out AWS completely — its free plan lasts 6 months at most (or until the $200 in credits is used up, whichever comes first), wrong fit for something I want to stay live indefinitely.
- Switched from Cloudflare R2 to Backblaze B2 for file storage. R2 needs a card or PayPal to activate — found that out by actually trying to sign up, not by reading about it. Checked B2 the same way before committing, across more than one source.
- Local disk for my own dev, B2 for anything real — the switch lives entirely inside `storage.py`, so nothing else in the app has to know or care which one is active. Looked at MinIO as the more "correct" version of this, decided it wasn't worth the extra setup right now.
- Turned on server-side encryption on the bucket, even though it means encrypted files are left out of Backblaze's snapshots (their docs say so for snapshots made from the Browse Files page). Fine trade — my actual safety net for this data is Neon plus my own hash verification, not a Backblaze snapshot.
- Pinned `redis` exactly (6.4.0). CI runs without Valkey, so the tests use the in-memory rate limiter and can't notice a redis release that breaks the Valkey connection. A newer major waits for a manual test against Valkey.
- Kept Valkey even though a single-instance deployment doesn't really need shared rate-limit storage yet. Decided that on purpose, for the practice, not by default. On Render I run without it (see below).
- Docker Compose is strictly for running things locally while I develop — never how this actually gets deployed. Realizing that early saved me from a lot of confused assumptions later.
- Multi-stage Dockerfile, on purpose: build tools stay isolated in a throwaway first stage, only the finished venv and real code make it into the final image. Smaller image, smaller attack surface — matters more given the direction I'm taking this project.
- Chose the slim base image over alpine specifically because psycopg2 has known install friction against alpine's C library. Slightly bigger image, avoided a real, well-documented headache instead.
- Postgres and Valkey both pinned to major-version-only tags, not an exact patch and not a floating "latest". The Python packages are different: those are pinned exactly (see Security tooling).
- Postgres's port is published only on `127.0.0.1` (so pytest on my machine can reach it), never on all interfaces. Everything else reaches it through the container network.
- The API container doesn't mount a live folder from my host — it builds as a sealed snapshot, matching what will actually run later, rather than being optimized for live-reloading convenience. Worth reconsidering once Docker's basic proof is further along, not settled forever.

- Migrations run when the container starts, not as a separate Render step. Render's free plan locks the Pre-Deploy Command (the dashboard says it's for paid instances). So `scripts/start.sh` runs `alembic upgrade head` first and only then starts the app, and `set -e` makes the container stop if the migration fails, instead of serving an app that doesn't match its database. I tried that locally with an unreachable database URL. The cost: every restart and every wake-up from sleep runs the migration check too.
- `PORT=8000` is set on Render on purpose. Render's default is 10000; on the first deploy it noticed my app on 8000 by itself and restarted the deploy once. Setting it removes the guess.
- Render runs without Valkey. `limiter.py` falls back to in-memory storage when `VALKEY_URL` isn't set, and with one worker that's enough. The limits start over on a restart. Valkey stays in Compose for local development.
- Render's Auto-Deploy is set to "On Commit", not "After CI Checks Pass". In that second mode Render only deploys when every check passes, and Trivy isn't required, so one red Trivy run would block every deploy. Changes only reach `main` through a pull request that has passed the four required checks, so "On Commit" isn't unchecked.
- Production secrets are generated in KeePassXC and pasted into Render's environment settings. They never go in the repo, and `.env.example` lists names only. The setup token is made fresh for the deploy and deleted from Render after its first use.
- I left bcrypt at cost 12 on Render. A hash takes about 0.2 s on my laptop and about 1.6 s on Render's free CPU, so a login there takes about 2 s. Lowering the cost would make the demo faster by making password hashing weaker, which is the same reasoning as the test suite.
- No `render.yaml` for now. I created the service by hand in the dashboard, and a Blueprint can come later. I haven't checked whether Blueprints work cleanly on the free plan.

## Security tooling

- CodeQL runs through GitHub's default setup (Python and the workflow files) instead of a workflow file of my own. It's the same engine, but GitHub keeps the configuration, so there's nothing for me to pin or maintain. Its first alert was the audit-log fallback logging a patient ID when an audit-log write fails. I dismissed it with a comment: the line logs numeric IDs only, and when an audit row is lost that line is the only trace.
- Bandit runs in CI on `app/` and fails on medium severity or higher. Two Low findings stay on purpose: the `"bearer"` token type, which Bandit reads as a hard-coded password, and the silent `except: pass` in the upload cleanup (see `known-issues.md`).
- Trivy scans the built image for known vulnerabilities and leaked secrets on every pull request and every push to main, and again every Monday, because new CVEs appear against an image that hasn't changed. It fails the job on HIGH or CRITICAL findings and ignores vulnerabilities that have no fix yet. The first run found five HIGH ones, all in libraries bundled inside pip: their versions matched pip's own list of bundled libraries exactly. So the runtime image no longer includes pip. The Trivy action is pinned by full commit SHA: in March 2026 an attacker moved 76 of its 77 version tags to malicious code.
- Trivy is not a required check, on purpose. A new fixable CVE in the base image would block every merge, Dependabot's security PRs included, and nobody can bypass the ruleset. The weekly run still reports.
- Required checks on `main`: `lint`, `test`, `docker` and `bandit`. The CodeQL checks aren't required: on Dependabot's PRs CodeQL showed a neutral "configurations not found" result instead of running, so requiring them could leave those PRs stuck. "Branch must be up to date before merging" stays off; I merge one PR at a time and CI runs on each.
- Dependabot alerts, security updates and malware alerts are on. On its first day it found 24 known vulnerabilities in my pinned dependencies: two critical, and most of them in PyJWT. Merging its pull requests closed all of them within a day, and a smoke test against the real storage backend passed afterwards.
- Dependabot version updates: pip every three months, GitHub Actions and Docker every month, and always a seven-day wait after a release before it proposes it (security updates aren't delayed). FastAPI went from 0.146 to 0.156 in two days (18 to 20 October), and every batch of updates needs a smoke test, which I don't want to keep doing before the first deploy.
- Ignored on purpose: SQLAlchemy minor and major updates (2.1 makes psycopg 3 the default for `postgresql://` URLs and I use psycopg2, so that update failed CI at import), websockets majors (the API is REST only), redis majors (no Valkey test yet), and boto3, botocore and s3transfer entirely, because CI can't test Backblaze. I bump those three together by hand after a smoke test. Security updates for all of them still arrive.
- Every Python package in the image is pinned exactly. Dependabot only edits lines that already exist, so a new dependency of an updated package (`opentelemetry-api` came in with FastAPI) slips past it. When that happens I regenerate the file from the image.
- The CI test key is generated on each run and hidden in the logs. The database password for the throwaway CI database is still written in `ci.yml`.
- The container runs as an unprivileged user (uid 1000). The only folder I made writable for it is `/app/uploads`. `.dockerignore` keeps tests, dev files, caches and `.github` out of the image.
- On 2026-11-05 Trivy went red because of the base image, not my code: `python:3.14-slim` shipped `apt` 3.0.3 and Trivy flagged `CVE-2026-109518` (HIGH), which is fixed in 3.0.4. This is the situation I made Trivy non-required for: the four required checks stayed green, so merging and deploying went on. By 2026-11-06 a fresh pull of the base image had `apt` 3.0.4, so the next Trivy run should pass. Had it stayed red, I would have upgraded `apt` in the Dockerfile or added a `.trivyignore` entry with a reason and an expiry date. Either way Trivy stays non-required.

## Closed before the first deploy

Three problems I found while writing tests and reading the code. I fixed them before the service went online.

- **The first SuperAdmin now needs a setup token.** On a fresh deployment the bootstrap route needed no login, so whoever called it first would have become SuperAdmin. I could have left it open and called it myself right after deploying, or removed the route and created the first SuperAdmin by hand in the database. I chose a one-time secret instead: the request must send a header called `X-Bootstrap-Token` that matches the `BOOTSTRAP_TOKEN` setting on the server.
- **How the check works.** It runs first, before the app touches the database, and it reads the setting at the moment the request arrives. If the setting is empty or missing, everyone is refused. A plain "are the two values different?" check would let everyone in when both are empty. The values are compared with `secrets.compare_digest`, which takes the same time however many characters match. A wrong, a missing and an unconfigured token all get the same 403 `Invalid setup token`, so the answer doesn't reveal whether a token is set. I kept the check inside the route function so the limit of 3 tries per minute counts failed guesses too.
- **How it went on Render.** I generated a fresh token, called the route once, deleted the token from Render and redeployed. The old token now gets a 403.
- **Deactivated accounts can no longer log in.** Before, they got a token that was useless everywhere else, the audit log said `LOGIN_SUCCESS`, and the person learned their password was right. Now `login` refuses them with the same 401 `Invalid credentials` as a wrong password and logs `LOGIN_FAILED`. The check comes after the password check, so a deactivated account and a wrong password look identical from outside. On Render, the throwaway test account got a 401 after I deactivated it.
- **Uploads must start like the file type they claim to be.** The extension alone was trusted, so any file could be called `.pdf`. Now a small table lists the bytes each allowed type must start with: `%PDF-` for PDF, the 8-byte PNG signature, `ff d8 ff` for JPEG, and `DICM` at byte 128 for DICOM (checked against Part 10 of the DICOM standard). A test makes sure the table and the allowed extensions list the same types.
- **What the upload check doesn't do.** It only looks at the first bytes, so a real header followed by junk still passes. Downloads are protected by the download route, which sends every file as a plain attachment (`application/octet-stream`), so a browser saves it instead of opening it. The check is also strict: DICOM files without the 128-byte header are refused, and so are empty files. I wrote the table by hand because `imghdr` was removed in Python 3.13 and `libmagic` needs a system library I didn't want in the image.

## Client IP behind Render

- **The problem.** Behind Render's proxy the app only saw an internal Render address, not the visitor's. Rate limits and the audit log both use that address, so every visitor would have shared one rate-limit counter, and every audit row would have shown the same IP.
- **What I chose.** `scripts/start.sh` gives uvicorn a list of proxies whose "who is calling" header (`X-Forwarded-For`) it may believe: `127.0.0.1`, `10.0.0.0/8` (Render's internal addresses) and Cloudflare's published ranges (15 IPv4 and 7 IPv6, copied from cloudflare.com/ips on 2026-11-04). uvicorn reads that header from the right and skips addresses on the list, so anything a visitor writes at the left end is ignored.
- **What I turned down.** Trusting everyone (`--forwarded-allow-ips="*"`): uvicorn then takes the leftmost address, and Render keeps whatever the visitor sends there, so a visitor could fake it, dodge rate limits and put a false address in the audit log. Trusting only Render's internal address: that gives a Cloudflare address, because requests pass through Cloudflare too. Reading Cloudflare's `CF-Connecting-IP` header: only safe if the app can't be reached except through Cloudflare, and I couldn't confirm that.
- **Deploy first, fix right after.** The fix can only be tested on Render, so I deployed first and didn't share the URL until the audit log showed the right address.
- **The first attempt failed, and the audit log showed it.** A list given to `--forwarded-allow-ips` replaces uvicorn's default of `127.0.0.1`, and on Render requests reach the app from `127.0.0.1`. I had left it out, so the header was ignored and the audit rows showed `127.0.0.x` addresses. My local tests didn't catch it. The second attempt added `127.0.0.1`. I then made two requests, a normal one and one with a faked `X-Forwarded-For: 6.6.6.6`. Both were logged (audit rows 27 and 28) with my real public address, and `6.6.6.6` never appeared. The weak spots of the list are in `known-issues.md`.

## Audit logging

- Didn't add a field to track what a value changed from and to. Considered it for things like specialty updates, but these are rare, low-stakes admin actions where I can just look at the current value directly — not worth the extra column.
- Left `action` as plain strings for now instead of building a shared list of valid values. Confirmed it's not a security risk — nothing external ever touches this field — so it's really just a maintenance nice-to-have I'm putting off.
- `entity_type` not always matching `entity_id`'s real table is intentional, not sloppy — I'd rather log a real value that happens to belong elsewhere than log a meaningless placeholder just to keep the two fields "matching."
- When I hardened the logging function against its own commit failing, I didn't try to make every log call in the codebase fully atomic with its business logic. Would've meant touching around 40 call sites for a benefit that only really applies to a third of them. Fixed the actual dangerous part instead — a logging failure can no longer crash a request or hide a success — and left true atomicity for later, if it ever actually matters.
